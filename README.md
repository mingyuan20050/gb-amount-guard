# GB-Amount-Guard · 大湾区跨境交易金额智能提取与异常资金识别系统

[![Python](https://img.shields.io/badge/Python-3.9%2B-blue)]() [![LLM](https://img.shields.io/badge/LLM-Prompt%E6%8A%BD%E5%8F%96-green)]() [![License](https://img.shields.io/badge/License-MIT-lightgrey)]()

用大模型从跨境交易流水附言、SWIFT 报文摘要、合同条款等**非结构化文本**中抽取金额与币种，完成币种归一化后，用可解释规则引擎标记大额、结构化拆分（化整为零）、高风险地区等可疑交易，并自带**字段级抽取评估闭环**（LLM vs 正则 baseline 对比）。

> **一句话：脏文本进 → 结构化金额出 → 风险分与审计报告落袋。**

---

## 一、项目背景

粤港澳大湾区日均跨境资金往来规模庞大（跨境理财通、深港/珠澳贸易结算、跨境电商收付），银行与支付机构的交易文本来源杂：流水附言、SWIFT MT103 报文摘要、纸质合同 OCR 段落……金额书写形态极不统一——

- `HK$1,234,567.89`（千分位 + 符号）
- `人民币贰拾伍万陆仟元整`（中文大写，合同惯例）
- `500万港元` / `US$1.2M`（数量级缩写）
- `定金20万港元，尾款80万港元，合计HK$1,000,000`（多金额干扰）

传统正则/模板抽取维护成本高、泛化差；而反洗钱（AML）场景又要求**每一笔可疑结论可解释、可回溯**（监管审计要求），纯黑盒模型不可接受。本项目面向这个矛盾，给出「**LLM 负责理解文本，规则引擎负责可解释风控，评估闭环负责量化效果**」的工程方案。

## 二、业务价值

| 价值点 | 说明 |
|---|---|
| 降本 | 非结构化文本金额抽取自动化，替代人工录单/核单 |
| 合规 | 大额、拆分、临界规避、高风险地区四类可疑模式自动标记，命中规则逐笔可解释，满足审计回溯要求 |
| 可量化 | 模拟数据自带 ground truth，抽取效果有字段级准确率，Prompt/模型迭代有回归测试，不是"感觉变好了" |
| 可演进 | 阈值、汇率、高风险地区名单全部集中在 `config.py`，换监管口径只改配置不动代码 |

                           ▼
┌─────────────────────────────────────────────────────────────────┐
│  抽取层  utils/llm_extractor.py                                  │
│  主通道：LLM Prompt 抽取（JSON Schema + few-shot + 自愈重试）     │
│  降级通道：正则 baseline（千分位/万单位/符号缩写/引导词）          │
│  输出：amount / currency / 判定依据 / 歧义处理备注                │
└──────────────────────────┬──────────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│  归一化层  utils/normalizer.py                                   │
│  币种别名归一（"港币/HK$"→HKD）+ 汇率折算等值CNY                  │
└──────────────────────────┬──────────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│  风控层  utils/risk_rules.py（可解释规则引擎，分数=规则加权和）   │

│  R4 临界规避(申报线90%~100%) +30 │ R5 夜间交易 +15 │ R6 数据质量  │
│  → risk_score / risk_level / risk_reasons（逐笔可回溯）          │
└──────────────────────────┬──────────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│  评估层  utils/evaluator.py  ＋  呈现层  utils/visualizer.py      │
│  字段级评估(vs ground truth)：金额(容差1%) / 币种精确匹配         │
│  按5种书写形态分组定位短板；LLM vs 正则 baseline 同表对比         │

**LLM 接入**：OpenAI 兼容协议，默认对接阿里云 DashScope（通义千问 qwen-plus），环境变量一键切换任意兼容端点（DeepSeek / Moonshot / OpenAI / 本地 vLLM 均可）。

## 四、核心设计亮点（不是 demo 的理由）

1. **双通道抽取 + 自动降级**：LLM 失败（限流/格式错）自动降级正则并在结果中标注 `llm_failed→regex`，风控端对抽取失败记录打 R6 数据质量分——生产思维。
2. **自愈式 JSON 解析**：模型输出不合法时，把原始回复与解析错误回喂模型修正，最多重试 2 次，而非直接丢弃。
3. **Prompt 即资产**：System Prompt 中固化输出 Schema、万/亿换算规则、多金额取舍规则、币种判定优先级，配 3 个 few-shot 覆盖大写/多金额/隐式币种三类 hard case。
4. **评估闭环**：模拟数据自带标签 → 字段级准确率 → 按书写形态分组找短板 → 双通道对比。这套东西本质是一个轻量 LLM 抽取评测集，Prompt 一改就能回归。
5. **可解释风控**：每笔可疑交易的 risk_reasons 写明命中规则与数值（如 `R2结构化拆分(同日5笔累计170万)`），不是黑盒分数。

## 五、快速开始

```bash
git clone https://github.com/mingyuan20050/gb-amount-guard.git
cd gb-amount-guard
pip install -r requirements.txt

# 方式一：LLM 模式（推荐，需 API Key）
cp .env.example .env        # 填入 LLM_API_KEY（阿里云 DashScope / 任意 OpenAI 兼容端点）
python main.py

# 方式二：离线 mock 模式（无需 Key，正则 baseline 走完整闭环）
python main.py --mode mock

# 其他
python main.py --regen --n 200   # 重新生成模拟数据
python utils/data_generator.py   # 只生成数据
```

**运行产出**：

- `data/processed/extracted_llm.csv` —— 结构化抽取+风控结果
- `outputs/risk_report.md` —— 审计报告（总体统计 / 规则命中 / TOP10 风险 / 评估明细）
- `outputs/*.png` —— 币种分布、金额分布、风险画像、每日资金流、汇总看板

### 实测效果（210 条：198 笔流水 + 12 份合同，qwen-plus，2026-10 实测）

| 抽取通道 | 抽取成功率 | 金额准确率 | 币种准确率 |
|---|---|---|---|
| LLM（qwen-plus） | 100% | **99.5%** | **100%** |
| 正则 baseline | 100% | 83.8% | 97.1% |

按书写形态分组（LLM 通道）：中文大写 / 千分位 / 符号缩写 / 多金额干扰 四类形态金额准确率均为 **100%**，万为单位形态 98%（唯一失分为 `21,256 欧元` 渲染成 `2.1万欧元` 后的千位精度损失，相对误差 1.2% 超出 1% 容差，属文本固有精度而非模型错误）。

正则 baseline 的失分集中在**中文大写**与**多金额取舍**（定金/尾款干扰）两类形态——这正是 LLM 的价值所在，也是本项目做双通道对比实验的结论：**规则化形态交给规则，语义歧义交给 LLM**。

## 八、面试讲解要点

**Q1：为什么用 LLM 而不是正则？**
项目实测：正则 baseline 金额准确率 83.8%，失分集中在中文大写换算和多金额取舍（"定金20万、尾款80万、合计100万"取哪个），LLM 在这些难例形态上是 100%。但正则在规则化形态（千分位、符号前缀）上零成本且稳定，所以最终架构是**双通道：LLM 主通道 + 正则降级**，各取所长。

**Q2：LLM 输出不稳定怎么保证可靠？**
四层防御：temperature=0；System Prompt 固化 JSON Schema + "只输出 JSON"；解析失败把错误信息回喂模型自愈重试；仍失败自动降级正则并打数据质量风险标记（R6），不让坏数据静默流过。

**Q3：拆分交易（smurfing）怎么识别？**
业务上"同一付款人把大额拆成多笔、单笔压在等值 5 万美元申报线下"。实现上按付款人+自然日 groupby，窗口内 ≥3 笔、每笔 < 申报线且累计 ≥ 申报线即命中 R2。阈值全部收在 config，换监管口径不改代码。

**Q4：怎么评估效果？**
模拟数据自带标签，做字段级评估：金额按相对误差 1% 容差判命中，币种精确匹配；再按 5 种书写形态分组，能定位到"模型到底弱在哪种形态"，Prompt 改一版跑一次回归，效果变化可量化。

**Q5：这个项目和真实生产的差距？**
汇率是静态演示牌价（生产接实时 API）；规则引擎是行级静态窗口（生产会做滑动窗口+图谱关联，识别跨机构拆分）；LLM 部分可换成微调后的小模型降本。主动讲差距比被问出来好。

## 九、局限与演进方向

- **汇率实时化**：`config.FX_RATES` 换成汇率 API + 本地缓存
- **流式与增量**：当前为批处理，可改为消息队列逐笔消费 + 滑动窗口拆分检测
- **模型降本**：高频规则化形态走正则预筛，仅歧义样本进 LLM（当前架构已预留通道标记）
- **关联分析**：引入主体图谱，识别跨账户、跨机构的关联拆分
